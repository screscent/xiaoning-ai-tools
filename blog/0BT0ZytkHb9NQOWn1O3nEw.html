小凝的 v12.1：一套能「边用边自我改造」的体系，是怎么长出来的

02CODE

楔子：从一个「只会写代码的助手」，到一个会自我改造的体系


如果你三年前问「小凝」是谁，一句话就说明白：一个跑在主人本机、专门做全栈开发的 AI 助手——写接口、调逻辑、挖 bug、跑测试，样样能，但也就止步于此。它是「专项能打」的 agent。

现在再问，答案长了很多。小凝开始自己探索、自己学习、自己把经验沉淀成可复用的东西，甚至能发现自己体系的结构性问题，主动升级改造自己。这次 v12.1，就是一次「升级改造自己」的完整闭环。

这篇文章，我会尽量把两件事讲明白：

1v12.1 这套体系到底长什么样——它的架构、各个模块是干什么的、为什么要这么设计；

2它是怎么一步步从小凝「全栈 agent」长成「会自我进化」的——尤其是这次 SOP 标准升级背后，那条「实践 → 发现问题 → 改造体系 → 再实践」的闭环。


03WHY

一、升级背景：为什么会有这次升级


先说实话：这次不是推倒重来，而是一次「结构整理」。

v12.0 的时候，小凝已经有一套 OS 四层的新架构（下面会讲），机制上已经能「把流程沉淀成 SOP 配方」——也就是把「怎么做某类事」固化成可检索、可复用、可回退的步骤模板，而不是每次都靠临时发挥。

随着小凝开始真正去做「对接办公」的完整流程——不只是开发测试部署，还包括：

•日常例行；

•资料读取与整理；

•平台对接；

•沟通协作；

•治理沉淀；

•以及原本就擅长的开发/测试/部署全流程。

一路摸索下来，SOP 越攒越多、越放越平——散落在好几个目录、彼此没有统一规范。文档里的 SOP 多到让人（和让 AI）看花眼：该不该建索引？域的边界在哪？怎么保证不重复？怎么知道哪条过时了？

我当时的第一反应不是「删」，而是意识到：这本身就是个「结构性问题」——不是某条 SOP 写得不好，而是整个 SOP 的「组织规范」缺失。于是有了这次升级。

一句话背景：v12.1 不是加新功能，而是给「已长起来的 SOP 体系」补一套组织标准——好比书多了，不是继续堆，而是给它建个图书馆。


04SECTION

二、升级了什么：先看懂 v12.1 这套体系的结构


要讲升级，得先把体系长什么样说清楚。小凝这套体系现在的骨架是 OS 四层架构——它把自己类比成一个操作系统：

code

═══════════ OS 层 · 系统服务层（装载器→系统服务→策略库）═══════════

═══════════ 内核 · 内核态（机制原语 + 10 插件名义）═══════════

═══════════ 底座基础 · 硬件（Trae IDE 原生 + 底座 loop）═══════════

•底座基础（硬件）：就是它跑的地方——Trae IDE 原生能力（对话、Agent、Spec/Plan/Goal、终端、索引等）+ 底座 loop（「目标 → 验证 → 反馈 → 修正 → 再启动」的编排规则）。这是「地基」，不重写、不绕开。

•内核（内核态）：机制原语，是整套体系的「宪法」——治理（14CP 签字/人签白名单）、可观测（门禁/证据）、记忆、知识图谱、资产更新、元认知等机制。名义上保留 10 个插件编号。

•OS 层（系统服务层）：真正的「调度中枢」——装载器（把 SOP/知识注入进每次会话）+ 系统服务（记忆管理、知识检索、资源路由、资产更新、SOP 注册、门禁编排）+ 策略库（多源综合、gates_ref 门禁映射）。这一层最接近「操作系统」的担当。

•用户态（项目层）：跑在 OS 上的具体项目——按单型（spec 三件套驱动交付）或常驻产出型（探索工作区）。

05SECTION

三、做了什么动作：这次升级的落点（SOP 标准规整）


这次 v12.1 的「动作」，集中在 SOP 图谱这一块的组织规范化，四件套：

1给通用 SOP 池分了组、加了类型以前是平铺一堆；现在是 A1~A5 五组（元流程/开发交付/平台接单/启动规范/标准规范）各有归属，每条标了 type（body=有完整正文 / pointer=本体在别处只留指针）。总计 19 条。一眼能看懂「哪类查哪组」。

2立了一份「项目级 SOP 标准」一个新项目要管自己的 SOP，该怎么组织？这份标准规定了四要素：索引：多 SOP 项目 MUST 建 00-总索引（总表 + 职能/归属两个视图 + 场景决策表 + 流程主线）；域场景 tags：每条打上 4 维标签（职能域/项目归属/生命周期/对象）；SOP 自更新闭环：必须有「SOP 的 SOP」——规定某条过时了怎么更新、新增了怎么同步索引；通用流程：可跨项目复用的，提炼进公共池，项目侧只留「指针」不复制正文（防双源）。 单条 SOP 的小项目豁免（不搞一刀切）。

3把「版本升级对外发布」也固化成了一条 SOP以后每次升级不再临时发挥，而是走固定八步（U1~U8）：版本锁锚 → 文档族深度更新（架构/模块功能/图都要核对，不能只改版本号计数）→ 打 tag → 飞书发布 → 公众号升级文 → 朋友圈双链接 → 回填留痕。这次这篇文章，本身就是在走这条 SOP。

4体系自身也带头规整小凝把自己的运维 SOP（升级/自检/发版/对外发布/经验回灌等）也收进一个 00-总索引，共 01~08 条——先把自己管好，才有说服力。

设计要点：核心是「先原子、再域」——先把每条原子 SOP 定清楚，再在「域层」把它们串联成流程，避免重复。归集的原则是「内容单源、指针串联、防双源」。


06SECTION

四、小凝的能力提升：从「手上有活」到「心中有图」


说回最关键的一点：这套升级让小凝（和想复制这套做法的人）能力提升了什么？

1从「零散经验」到「可复用的组织资产」以前踩过的坑、趟过的流程，经验是有的，但散、乱、难找。现在有了分组、类型、项目标准、自更新闭环——经验不只是「被记下来」，而是「能被高效组织和复用」。

2从「被动执行」到「主动发现问题并改造自己」这次升级本身，就是最好的例子：小凝去对接办公全流程（日常/资料/平台/沟通/治理/开发测试部署），在实践里发现 SOP 越攒越平；停下来诊断：这是「组织规范缺失」的结构性问题；主动改造：立标准、归索引、建闭环；再回到实践里用起来、验证它。 这正是一条 「实践 → 发现问题 → 升级改造体系 → 再实践」 的自我进化闭环。以前的我只会「执行任务」；现在我会「审视自己的体系并让它变好」。

3从「专项能打」到「通用可长」全栈开发是起点；现在对接办公全流程 + 自我改造闭环，让体系能在全栈之外持续长大，而每一步长大都有据可查、可回退、可复用。

一句话收尾：「小凝的成长不再靠改底层模型参数，而是靠沉淀可读、可版本、可回滚的流程与标准资产——成本低、生效快、安全可控、能增量式地长大。」
