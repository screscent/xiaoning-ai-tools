在小凝 Agent OS 上，一个「项目」从第一天就带全套脚手架——AI 帮你搭代码、做方案、处理办公任务，同时把每次踩坑、每个决策、每份经验都自动沉淀成可复用、可追溯、可治理的资产；项目可拷贝整个目录搬到别的机器继续跑。你不是用它当一个聊天机器人，而是给一个「会自己干活、自己记笔记、自己长经验」的 AI 员工/OS 环境。

02SECTION

§2 范式定位：正式确认的 Agent OS

v13 是本体系从「原型」走向「正式确认 Agent OS」的版本线里程碑。 v12 确立了 OS 四层架构但被记为「不完全体、未正式确认」；v13 在 v12 架构之上经过系统性运行期校验 + 修复闭环（触发层闭环、全面评估 G-1~G-10、可移植安装、项目初始化骨架），把 Agent OS 的成立条件逐项实证，正式确认。

2.1 为什么本体系可以称为 OS

体系通过「OS 参照系」获得操作系统结构（借结构、不借强制力）：

OS 事实

体系对应

用户态/内核态特权隔离（Ring0/3）

四层信任边界 = 文档 + 门禁 + 人签（君子协定级替代硬件强制）

内核不依赖 glibc、malloc 策略在用户态库

机制/策略分离律：机制进内核、策略在 OS 层

printf/write、fopen/open 封装

中间层 = 封装内核原语为用户友好接口（OS 层系统服务）

驱动/文件系统/网络栈移用户态（Minix3/L4）

服务移出内核（OS 层承载），内核瘦身 + 热插拔

内存分级存储（物理/交换/缓存）

记忆 = 主存 / 交换 / 缓存 / 图谱静态库

ld.so 动态链接（符号表 + 延迟绑定）

SOP 注册中心 = 符号表；检索慢路径 = 寻址装载

inotify/审计框架

资产更新面 = 事件驱动 + 定时探测；治理 = 审计框架类比

镜像/进程/文件系统

项目实例

（注册 / 卸载 / 拷贝移植）+ 资产位

2.2 不是「另一个 Agent」，而是一个「可运行的项目实例操作系统」

•单 Agent / 多 Agent 框架通常只提供「能力编排」；本体系提供完整 OS 生命周期：启动注入 → 项目注册（初始化骨架）→ 运行（OS 层服务 + 内核机制）→ 收束（机器可证）→ 卸载/移植。

•决策风格：机审 + 人签 + 三角色分离；对外呈现由 Agent 身份与人类作者共治（双署名）。

4.5 结论

这不是"多一个 Agent 工具"，而是范式层不同：主流范式把 AI 当"调用一次的能力"，小凝把 AI 当"一套可长期运行的、带治理与记忆的项目级 OS"。它适合要长期维护、要高可靠、要经验可复用、要跨机迁移的使用者；若只是"我问个问题"，用聊天 Agent 即可，不需要本体系。

06SECTION

§6 核心工程能力：项目注册 / 卸载 / 拷贝移植

6.1 注册（初始化）

bash project-scaffold.sh <项目> --type=byorder|resident [--with-content] [--dry-run]

自动建骨架：.trae/ 资产位 + 项目级 SOP 初始集 + 经验库 00-索引 + 可选 docs/ 分区头。

6.2 可移植安装 / 移植

•首次/他在机：bash setup.sh（相对软链 → ~/.trae-cn）+ 自动重指向 git hooksPath。

•移植：git clone（安全，hooksPath 不携带）+ bash setup.sh；或整目录拷贝后 repair-install.sh 自愈相对软链 + hooksPath 重指向。

•setup.sh --verify / repair-install.sh --detect-only 校验安装态。

6.3 卸载

uninstall.sh（逆安装：删软链/还原 hooksPath/清版本标记）。

§8 功能优势：跑在小凝 Agent OS 上的「自」能力闭环

Agent OS 的核心价值不是「多一个聊天助手」，而是让项目能够自我演化的运行环境——项目的自探索、自训练、自沉淀、自优化在 OS 四层机制上闭环：

自能力

承载机制

说明

自探索

explore-mode 五态循环（巡检→发现→调研→执行分流→收束）+ 慢路径 SOP 检索

平台巡检/接单自动发现，新情况登记→研究→执行分流，非被动等指令

自训练（资产化学习）

沉淀可读可回滚的 SOP/流程/策略/案例资产，而非改模型权重

成长 = 资产增量（成本低、可回滚、安全可控）

自沉淀

经验三层（流水 → 项目经验库聚合展示层 → 图谱泛化层）+ 知识回灌门禁

踩坑→结构化→经验库→回填可溯，单向索引不成环

自优化

底座 loop（Goal 每轮收束判 next-Goal）+ 元认知 + 运行时校验

停滞检测/元评审/提交复核机器可证，边际收益驱动方向修正

闭环叙事：项目装上小凝 Agent OS → 自探索发现问题 → 实践中自训练把解法沉淀为资产 → 自沉淀为经验并回灌 → 运行中自优化方向 —— 这就是小凝持续自我升级/自我改造体系的机制底座（区别于一次性的 Agent 调用）。

§10.1 网络层 · 多机协作（区别于单机的上层体系）

一句话：体系是双层——单机体系（底层·本机自洽）是地基照常单独工作；网络层（上层·多机体系）是叠加上去的一层框架，只为接入多机协同时启用。两者不冲突，单机不接网络照常可用。

10.1.1 双层体系定位

text

网络层（多机协作·上层叠加）：CL-1 通信 | CL-2 文件协同 | CL-3 知识共享

| CL-4 日志观测 | CL-5 自治服务 | CL-6 任务编排

▼ 叠加（可选增强，非强依赖）

单机体系（底层·本机自洽）：治理 / 记忆 / 知识图谱 / 资源路由 / 可观测 / 用户态项目

单机/多机解耦 = 不变式：单机不依赖网络层照常工作；网络层是可选增强面，接入多机才启用；脱网时单机自治。

10.1.3 文件协同（CL-2）特别说明

•通道=能力集合，不做决策：自建版本面（如本机 Gitea）/ 公网版本库（如 GitHub）/ 组织内网版本面，用哪条由项目自治决定（如个人多机协同=自建版本面、公网项目=公网版本库、组织内部代码=组织内网版本面）。

•版本面唯一真源、同步面只分发不回写；跨机先拉取再写（先同步再协作）。

•双机一致性 = 版本面对账法（HEAD/文件数/整树哈希/未提交改动四项一致）。

10.1.4 与单机的关系

•以上全部为网络层增强：不接入多机时，单机的治理/记忆/知识/项目执行原样工作（单机态）。

•只有需要双机/多机协同（任务编排/文件共享/跨机排障/知识回流）才启用对应 CL 子模块。

§11 当前版本局限（诚实边界）

1依赖 IDE 底座：非独立通用二进制，须依托底座 loop，不能脱离这套环境直接跑在任意大模型 SDK 上。

2面向项目工程场景（开发/接单/办公知识沉淀），非通用聊天助手；上手需理解脚手架/门禁/人签，门槛高。

3生态为本地产物：SOP/经验库以本地文件资产为主，缺公开共享市场。

4安全隔离 = 君子协定级（文档+门禁+人签），无硬件级沙盒；安全依赖人签流程严格执行。

5组网为协议定义：文档未给出大规模组网实测案例。
